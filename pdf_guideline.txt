3. Project Task and Technical Requirements 
Your task is to solve one real text classification problem (binary or multi -class) and show, with evidence, 
which preprocessing, representation and classifier choices work best for it. The project assesses CO2: Apply 
a t ext preprocessing pipeline, statistical language models, word representations (BoW, TF -IDF, 
embeddings), and appropriate evaluation metrics to solve text -analytics problems on real -world 
English/Bangla data (PO-a4.C3). 
Scope. Use only the techniques covere d in Weeks 1 –5: regular expressions, preprocessing, Bag of Words, 
TF-IDF, Naive Bayes and other classical classifiers, and word embeddings. Transformer models (BERT, GPT 
and similar) are not allowed in the mid-term project; they belong to the final-term project (CO4). 
Every project must include the following components. 
1. Problem and dataset 
– A clearly stated classification problem with a real-world use case. 
– At least 2,000 labelled documents and at least 2 classes, in English, Bangla or both. Bangla 
datasets are encouraged. 
– Cite the dataset source and confirm its licence allows academic use. 
2. Exploratory data analysis (EDA) 
– Class distribution (state whether the data is imbalanced), document -length statistics, and the 
most frequent words per class before and after preprocessing. 
– At least three figures, each with a one-line interpretation. 
3. Preprocessing pipeline 
– Implement it as a reusable function and justify each step: cleaning with regular expressions 
(URLs, emojis, numbers, HTML), tokenisation, case folding (En glish), punctuation and stop-word 
removal, stemming and/or lemmatisation. 
– For Bangla, handle Unicode normalisation and use a Bangla -specific tokeniser and stop -word 
list; discuss the limitations of stemming in Bangla. 
– Run an ablation: compare at least two pipeline variants (e.g., with vs without stop -word 
removal, or stemming vs lemmatisation) and report their effect on macro-F1. 
4. Text representations (all three are required) 
– Bag of Words (count vectors). 
– TF-IDF, including at least one n-gram setting (e.g., unigram vs unigram + bigram). 
– Word embeddings: average Word2Vec vectors trained on your corpus, or pretrained 
FastText/GloVe vectors (FastText provides Bangla vectors). 
5. Classifiers 
– A majority-class baseline. 
– Multinomial Naive Bayes on BoW and TF-IDF (required).

– One more classical classifier applied to all three representations: Logistic Regression or Linear 
SVM. Use Logistic Regression or Gaussian Naive Bayes for embeddings, since Multinomial Naive 
Bayes cannot take negative feature values. 
– Tune at least on e hyperparameter per model on the validation set (e.g., Laplace smoothing 
alpha, C, max_features). 
– Justify your choice of representations and classifiers for your problem, data and language, and 
explain what the comparison shows. 
6. Evaluation protocol 
– Stratified train / validation / test split (70/15/15) or stratified 5-fold cross-validation, with a fixed 
random seed. 
– Fit vectorisers and tune hyperparameters on training/validation data only; touch the test set 
once, at the end. 
– Report accuracy, macro-precision, macro-recall and macro-F1 for every model, plus a confusion 
matrix for the best model. Macro-F1 is the primary metric. 
– Present results in one comparison table: rows = representation + classifier, columns = metrics. 
7. Error analysis and interpretation 
– List the 10 most informative words per class from Naive Bayes (log-probability ratio). 
– Inspect at least 20 misclassified test examples and group them into error types (sarcasm, 
negation, code-mixed Banglish, label noise, etc.). 
8. Code documentation and explanation 
– Organise the notebook into clearly titled sections (EDA, preprocessing, representations, models, 
evaluation, error analysis). Before each code cell or block, add a Markdown cell explaining what 
it does and why; comment the key lines. Every memb er must be able to explain any cell in the 
viva. 
9. Colab-ready notebook (no dependencies) 
– Submit the code as a single .ipynb notebook that runs top to bottom on Google Colab (Runtime 
→ Run all) with no manual setup: no local files, no file uploads, no separate requirements file. 
– Load the dataset inside the notebook from a public Google Drive or GitHub link; a dataset found 
on Kaggle, Hugging Face or UCI must be hosted on Google Drive or GitHub first. If a library is not 
preinstalled on Colab, install it with a pip cell at the top of the notebook. Fix random seeds so 
results can be reproduced.

Individual moderation through viva. The viva is not a separate criterion. I first score the group submission 
on each criterion above. In the viva (Section 7), each me mber is asked about the parts of the code and 
report that relate to each criterion, and their individual mark for that criterion is the group mark multiplied 
by a viva factor (the group mark is the ceiling): 
• Factor 1.0: explains the work correctly and confidently, including design choices. 
• Factor 0.75: explains most of the work, with minor gaps. 
• Factor 0.5: explains only parts of the work, with major gaps. 
• Factor 0.25: cannot explain the work meaningfully. 
How the other requirements are counted. Every component in Section 3 is evidence for one of the three 
criteria: 
• Preprocessing pipeline: EDA (component 2), the pipeline and its justification, Bangla-specific handling 
and the ablation (component 3). 
• Representation and modelling: the three representations, the classifiers, tuning and the justification 
of your choices (components 4–5), and the Colab notebook (components 8 –9). A notebook that does 
not run on Colab scores 0 on this criterion. 
• Evaluation and interpretation: the evaluation protocol, comparison table, confusion matrix and error 
analysis (components 6–7), and the discussion and conclusions in the report (Section 6).
